# 実験: ブロックカット木を使った上界

本体の README「限界と今後の改善案」で挙げた「より強い上界」を試作し、本体の上界と速度を比べた記録です。
**結論: 探索の各ノードで毎回計算する形では、探索ノード数は最大 61% 減ったが、1 ノードあたりの計算が約 4 倍重くなり、全ケースで遅くなった。そのため本体には採用しなかった。**
ブロックカット木そのものが役に立たないという意味ではありません。使う場面を絞る方法や、前処理として 1 回だけ使う方法は試していません（末尾の「採用するとしたら」を参照）。

## アイデア

今の上界は「この先行ける駅すべて」について、各駅の長い線路 2 本ぶんを足しています。
でも、その駅を消すと路線図が分かれる駅（関節点）の先にある枝には、経路は 1 本しか入れません。
別の枝に移るには関節点をもう一度通る必要があり、それは禁止されているからです。

そこで、まだ行ける部分を関節点で 2 連結成分（ブロック）に分け、ブロックカット木を作ります。
上界は、根（経路の端）から 1 本の道に沿って下りたときの最大値にします。
ブロックを見つけるには、Tarjan の lowlink を使う深さ優先探索を、探索の各ノードで実行します。

正しさの確認として、総当たりとの比較を 9,000 ケース行い、すべて一致しました。
上界が実際より小さく出ると正解を捨ててしまうので、それが起きていないことの確認です。

## 分かったこと

- **枝刈りは確かに強くなる**: 予想どおり鉄道網風（木に近い）グラフで効果が大きく、ランダムグラフでは小さかった。規模が大きいほど削減率が上がる傾向がある（hubs=81 で 61%）。
- **それ以上に 1 ノードが重くなる**: 1 ノードあたりの時間は、本体が約 12 µs、ブロック版が約 49 µs だった。差し引きで得をするには、ノード数を 75% 以上減らす必要があり、今回の範囲では届かなかった。
- **時間切れの入力でも出力は変わらなかった**: hubs=81 (seed 2) と hubs=100 では、どちらの版も同じ長さの経路を出力した。

## 採用するとしたら

- Rust や C++ のように 1 ノードの処理が速い言語なら、損益分岐が変わる可能性がある。
- 毎ノードで計算せず、探索の浅いところ（分岐が多く、刈れたときの効果が大きいところ）だけで使う。
- 毎回ブロック分解をやり直さず、差分だけ更新する（実装はかなり難しい）。
- **前処理として 1 回だけ使う（分割統治）**: 探索中ではなく、最初に路線図全体をブロックに分ける。閉路は必ず 1 つのブロックの中に収まり、経路はブロックカット木の 1 本の道に沿ってブロックを渡り歩く。そこで、ブロックごとに「入口から出口までの最長経路」を解き、最後に木の上で組み合わせる。時間のかかる部分が「一番大きいブロックの大きさ」で決まるようになるので、ブロックが細かく分かれる路線図なら大きく効く。ただし、幹線どうしが網の目につながって巨大な 1 ブロックになる路線図ではあまり効かない。入口と出口の全組み合わせを解く必要があり、実装も複雑になる。
